# Lessons

One line each time a task needed rework: the tester sent it back, CI failed twice, or a
human corrected something (G-0014). Newest last. The architect turns a lesson that repeats
into a proposed rule change for the harness.

`- YYYY-MM-DD T-NNNN <role>: what went wrong, and what would have prevented it`
- 2026-11-21 T-0002 architect: two Done-when lines could not pass as written (a log line the plugin always prints; a fake `siteId` that fails with a logged-in Netlify CLI). Run or read the tool once before writing a check about its output.
- 2026-11-21 T-0005 developer: the UX designer sent the search glow back (a dark-spined match was not clearly brighter than dimmed light books at 0.5). Before handing over, check the Design's own "when to adjust" condition against the screenshots, and apply its allowed adjustment when it is met.
- 2026-11-21 T-0009 developer: the favourites save reads the list, changes it and writes the whole list back, so two saves that overlap lose a star. The test called "at the same time" awaited between the two saves, so they never overlapped. A test for simultaneous writes has to start both without awaiting either (`Promise.all`), against the real server.
- 2026-11-21 T-0009 developer: a read-change-write of a whole field over PocketBase's REST API can't be made safe, even with a check after writing. Changes that two writers may make at once need a server-side transaction (a pb_hooks route with `runInTransaction`) or per-item modifiers, and a client queue so one device never overlaps itself.
- 2026-11-21 T-0009 developer: the new hook tests waited a fixed 60 ms for queued server calls, so `npm test` failed in 6 of 7 runs on a busy machine while CI happened to pass. Tests of async queues should wait for a condition (`vi.waitFor`) and drain or unmount each device before the next test, never sleep a fixed time.
- 2026-11-21 T-0009 developer: hook tests that waited a fixed 60 ms against a stand-in server with delays failed on a busy machine. Wait for a condition (the stand-in server quiet, or the expected state), and unmount and drain every device before the next test.
- 2026-11-21 T-0003 developer: three fixes in a row (#206, #207, phone-smooth-shelf) were guesses at why the shelf failed on Hanna's phone; the real cause (Chrome had blocked WebGL after earlier crashes) only showed once the error note printed its reason. When a failure only happens on a user's device, make the app show the reason first, then fix.
- 2026-11-21 T-0015 developer: the UX review sent back two cases the first build missed: typed country names spelled with only a first capital ("usa" → "Usa"), and one imaginary land counted twice under two names ("Hogwarts" and Open Library's long Hogwarts name). When a feature stores what a user types or groups names from two sources, test the short and long forms of the same thing and abbreviations, not only the happy spelling.
- 2026-11-22 T-0019 developer: the UX review sent back the swatch names: `colourName` named colours by hue alone, so the muted warm colours that darkened covers mostly give (a dusty brown-red, tan, saddle brown) came out as "Red" and "Orange". When code puts a name on something for people, test it on real data (here the real cover palettes from the screenshots), not only on clean textbook colours.
- 2026-11-22 T-0020 developer: the UX review sent back the Arrange bar covering the top of ★ Favourites. I had seen it in my own screenshots, called it "already there before, for the architect" and moved the drag shot to row 2 to work around it, though the new tools and the most likely drop line were behind it. When something in your own screenshots hides what the task adds, fix it in the task (here one CSS line: a sticky `top` inside a scroll container counts from inside its padding), don't frame the shots around it.
- 2026-11-22 T-0023 developer: the UX review sent back the pile switch's wrapped state: the design allowed it to wrap, but `.segmented`'s 999px pill radius turns a two-row box into a blob with a button sticking out, and I only screenshotted widths where it fit (with 4 px to spare). When a layout has a fallback (wrapping, overflow, a second row), make it happen once in the dev server (a narrower phone or larger text) and screenshot it, not only the widths where it doesn't trigger.
- 2026-11-22 T-0025 developer: the UX review sent back two CSS slips: a dimmed ‹ › still changed on hover, because the base `.btn:hover:not(:disabled)` doesn't know `aria-disabled` and outranks a two-class rule; and the zoom buttons I was told to copy were 38 px, which I measured and only logged. When a design asks for "exactly like X", copy X's measured result, and fix X when it misses the design's own size; and when "disabled" is `aria-disabled`, hover the dimmed control in the dev server and read its computed style, since `:disabled` rules won't cover it.
- 2026-11-23 T-0039 tester: sent back the tap zones: "a zone for every lit country whose box is under 44 px" missed France, whose bounding box includes French Guiana (59 × 45 px at 390) while mainland France is 12 × 8 px, so the sea beside it opened the Netherlands. Countries with far-away pieces (France, the USA, Norway…) break any rule that uses a country's whole bounding box; measure the piece people tap, and check one such country in the screenshots, not only the compact ones.
- 2026-11-23 T-0039 developer: the fix asked for "a tap 6 px off mainland France opens France", but at 390 France is ringed within 6 px by lit UK, Spain, Italy and Germany, so any fair rule must open the nearer neighbour there. Only measuring every point near France (216 points, France nearest at 4) showed that, after three runs that each "failed" a different way. When an expected result is about geometry on a crowded map, measure the distances around the target before tuning the rule, and write the check against what's actually nearest.
- 2026-11-23 T-0027 developer: the UX review sent back four of the 20 creatures (capybara read as a bear, the unicorn as a pig, the bookmark fox's ribbons as wings, the African penguin's chest spots as a mouth, and the bookmark fox's shiny ribbons vanished on midnight). The model test and my screenshots passed, but I only checked budgets, parts and that every tile rendered, and handed the "does it read as this animal?" question wholly to the reviewer. When agents produce visual work in bulk, look at each piece at its real size (120 px here) against its one-line description before handing over, and also check that the shiny's key feature shows on the darkest wallpaper; a passing test proves the structure, not the look.
- 2026-11-23 T-0039 tester: sent back the focus fix at the zoom limits: ⤢ pressed at 8× moved focus to +, which was still `disabled` until the next render, so the browser dropped the focus call and focus fell to the page. The developer tested + to 8× and − to 1×, not the one button that jumps from one limit to the other. When focus moves to a control whose disabled state changes in the same press, move it after the re-render (an effect on the new state), and test every button that reaches a limit from every other limit.
